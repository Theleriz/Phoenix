# PHOENIX план реализации MVP

## 1. Назначение документа

Этот документ является пошаговым техническим заданием для ИИ-агента, который будет реализовывать PHOENIX: веб-платформу дистанционной реабилитации после первичного эндопротезирования коленного сустава (primary TKA).

Основание: `PHOENIX_NTZ_TKA_v1.2.docx`.

Этот план имеет приоритет над противоречащими ему решениями из исходного НТЗ. В частности, в текущем MVP **не создаётся мобильное приложение**. Пациентский и врачебный интерфейсы являются веб-приложениями. Подключение и приём данных IMU выполняются отдельным локальным gateway-сервисом на backend-стороне; LLM развёртывается локально на серверной инфраструктуре.

## 2. Зафиксированные решения

| Область | Решение для MVP |
| --- | --- |
| Клиент | Веб-приложение для пациента и врача |
| Мобильное приложение | Не входит в MVP |
| IMU | Три 6-axis IMU: бедро, голень, стопа; имеется скрипт, который нужно исследовать и адаптировать |
| Приём IMU | Через отдельный gateway, а не напрямую из браузера |
| Развёртывание | Сервер; все сервисы контейнеризированы |
| AI | Локальная LLM на сервере, без обязательных внешних API |
| ML интерпретация движения | Локальная ML-модель как отдельный сервис; она интерпретирует калиброванные IMU-данные, но не заменяет safety rules |
| Организации | Мультитенантная архитектура с первого дня |
| МИС/EHR | Не входит в первый релиз, но интерфейс интеграции должен быть предусмотрен |
| Клиническая безопасность | Только детерминированные правила; LLM не принимает клинических решений |

### Важное ограничение топологии датчиков

Если сервер находится в дата-центре или облаке, он не может напрямую принимать BLE/USB-пакеты от IMU, находящихся рядом с пациентом. В такой конфигурации нужны два уровня:

```text
IMU датчики
  -> локальный gateway на ПК, мини ПК или edge-устройстве в зоне действия датчиков
  -> защищённое соединение
  -> центральный сервер PHOENIX
  -> веб-приложения пациента и врача
```

Если сервер физически находится рядом с датчиками и имеет нужные Bluetooth/USB-интерфейсы, gateway может работать на этом же сервере. ИИ-агент не должен предполагать наличие Bluetooth на удалённом сервере.

## 3. Цели MVP

Реализовать работающий замкнутый контур:

1. Врач создаёт пациента, эпизод лечения и назначает упражнения.
2. Пациент открывает веб-интерфейс и начинает сессию.
3. Gateway принимает поток трёх IMU, синхронизирует и передаёт его на сервер.
4. Backend считает доступные биомеханические метрики, повторения, качество сигнала и score.
5. Пациент получает короткий детерминированный feedback.
6. После сессии пациент отвечает на вопросы о боли и симптомах.
7. Backend запускает safety rules и создаёт alert при необходимости.
8. Врач видит динамику, alerts и может изменить план.
9. Локальная LLM объясняет только уже рассчитанные данные и готовит summary.

## 4. Границы MVP

### Входит

- primary unilateral TKA;
- роли пациент, врач, реабилитолог, администратор организации, research viewer и technical admin;
- мультитенантность: несколько организаций, клиник и врачей;
- упражнения с измеримыми IMU-параметрами;
- reference video, инструкция по размещению IMU и калибровка;
- live-статусы IMU, счётчик повторов, ROM, tempo, hold, Signal Confidence;
- Correctness Score и Execution Effectiveness Score;
- post-session pain/symptom check;
- doctor dashboard, назначения, alerts и audit trail;
- локальная LLM для patient feedback и clinician summary;
- RU/KZ/EN локализация.

### Не входит

- мобильное приложение;
- интеграция с МИС/EHR;
- автоматическая диагностика;
- автоматическое изменение назначений, ограничений, нагрузки или лекарств;
- компьютерное зрение, EMG, force plate, оценка силы мышц;
- утверждения о нагрузке на сустав, компенсации тазом/корпусом или двусторонней симметрии;
- predictive model delayed recovery;
- свободная генерация live-замечаний LLM.

### Предлагаемый стек

- Web: React, TypeScript, Vite или Next.js.
- API: Python FastAPI.
- Real-time: WebSocket; MQTT допустим между gateway и сервером.
- Signal processing: Python, NumPy, SciPy.
- Database: PostgreSQL.
- Cache and lightweight event state: Redis.
- Raw IMU and media storage: MinIO или совместимое S3-хранилище.
- Containers: Docker Compose для MVP; Helm/Kubernetes только если это потребуется после пилота.
- Local LLM: Ollama для простого запуска или vLLM при наличии подходящего GPU и нагрузке.
- Observability: OpenTelemetry, Prometheus, Grafana и структурированные JSON-логи.

## 6. Требования к мультитенантности

1. Создать сущности `Organization`, `Clinic` и `Membership`.
2. Каждая клиническая сущность обязана иметь `organization_id`.
3. Все запросы к пациентам, сессиям, назначениям, alert и экспортам фильтруются по организации на уровне backend, а не только UI.
4. Пользователь может состоять в нескольких организациях, но в каждом запросе действует в выбранном tenant context.
5. Врач видит только пациентов своей организации и назначенных ему пациентов.
6. У каждой организации свои настройки: контакты для urgent instructions, клинические пороги, локализация, шаблоны и branding.
7. Нельзя использовать глобальные идентификаторы пациента как единственный ключ доступа.
8. Research export всегда деидентифицируется и ограничивается organisation-level правами.

## 7. Этап 1: аудит текущего IMU-скрипта

### Задачи

1. Найти и изучить имеющийся скрипт без изменения его исходного поведения.
2. Описать его язык, зависимости, способ связи с датчиками, формат пакетов, частоту дискретизации, timestamp, reconnect и ошибки.
3. Создать документ `docs/imu/current-script-audit.md`.
4. Сохранить 3-5 коротких записей реальных пакетов в обезличенном формате для replay-тестов.
5. Выделить hardware-specific код в отдельный adapter.
6. Создать интерфейс `IMUAdapter`, чтобы конкретная модель датчика не проникала в остальную систему.

### Что уже известно о переданном скрипте

Скрипт использует `Bleak` для BLE, ищет похожие на WitMotion устройства и принимает 20-байтные пакеты с заголовком `0x55 0x61`. Из пакета извлекаются три значения акселерометра, три значения гироскопа и три угла `roll`, `pitch`, `yaw`.

Его можно использовать как основу gateway, но нельзя использовать функцию `interpret_movement()` как клиническую интерпретацию. В ней абсолютные пороги углов, например `pitch > 30`, назначают движение без учёта:

- конкретного места фиксации датчика;
- исходной позы пациента;
- стороны операции;
- локальной системы координат устройства;
- калибровки;
- относительного угла между бедром и голенью;
- качества сигнала и временной последовательности.

Для PHOENIX требуется заменить роли `Left_Arm`, `Left_Leg`, `Right_Arm`, `Right_Leg` на `THIGH`, `SHANK`, `FOOT` и дополнительно хранить сторону операции. Автоматически назначать найденные MAC-адреса ролям нельзя: пользователь или технический специалист должен подтвердить роль каждого физического датчика.

### Обязательная переработка скрипта

1. Сохранить исходный скрипт неизменённым в `legacy/` и добавить лицензию/происхождение, если они известны.
2. Создать новый сервис `services/imu-gateway` на его основе.
3. Добавить gateway timestamp, монотонный sequence number и ID сессии к каждому принятому пакету.
4. Проверять длину, заголовок и checksum пакета по документации датчика; не считать пакет валидным только по `0x55 0x61`.
5. Сохранять raw accelerometer и gyroscope значения вместе с углами, а также их scale/range и частоту дискретизации.
6. Не подавлять исключения через `except Exception: pass`: классифицировать ошибки, логировать их, отражать reconnect и причину отключения.
7. Не выбирать первый найденный notification characteristic без конфигурации: после первичного discovery зафиксировать модель, service UUID и characteristic UUID в настройках adapter.
8. Заменить терминальный dashboard на API/WebSocket события; терминальный вывод оставить только диагностическим режимом.
9. Добавить controlled shutdown, отмену фоновых задач, heartbeat, reconnect backoff и локальный durable buffer.
10. Не использовать абсолютные `roll/pitch/yaw` пороги для медицинских заключений, score или live-cues.

### Недостающие данные, которые нужно получить до hardware-интеграции

- оригинальный файл скрипта `.py` без искажений форматирования;
- модель каждого датчика;
- официальный packet protocol для `0x61`, включая checksum;
- частота дискретизации, диапазоны accelerometer/gyroscope и scale factors;
- порядок осей и система координат;
- способ синхронизации часов трёх устройств;
- service UUID/characteristic UUID и допустимое количество параллельных BLE-подключений на gateway-host.

### Минимальный контракт адаптера

```python
class IMUAdapter:
    async def discover(self) -> list[SensorInfo]: ...
    async def connect(self, sensor_id: str) -> None: ...
    async def stream(self) -> AsyncIterator[RawIMUPacket]: ...
    async def disconnect(self, sensor_id: str) -> None: ...
```

### Результат этапа

- Текущий скрипт сохранён без регрессий.
- Есть replay-режим без физического IMU.
- Есть спецификация raw packet contract.
- Любая дальнейшая модификация скрипта покрыта тестом на записанном потоке.

## 12. Этап 6: IMU Gateway

Gateway обязан:

1. Подключать нужные датчики через текущий скрипт и adapter.
2. Назначать каждому устройству роль `THIGH`, `SHANK` или `FOOT`.
3. Нормализовать пакеты к единому контракту.
4. Проверять sequence number, потери, дубликаты и out-of-order packets.
5. Выполнять/фиксировать межсенсорную синхронизацию.
6. Буферизовать данные локально при потере связи с сервером.
7. Безопасно пересылать события на сервер.
8. Поддерживать `simulator` и `hardware` режимы.

Нормализованный пакет:

```json
{
  "device_id": "imu-thigh-001",
  "sensor_role": "thigh",
  "timestamp_device": 0,
  "timestamp_gateway": 0,
  "sequence_number": 0,
  "ax": 0,
  "ay": 0,
  "az": 0,
  "gx": 0,
  "gy": 0,
  "gz": 0,
  "battery": 0
}
```

**Готовность:** replay трёх потоков проходит весь путь от gateway до WebSocket и сохранения raw chunks.

## 13. Этап 7: калибровка, синхронизация и Signal Quality

Перед стартом упражнения система проверяет:

- три нужных датчика подключены;
- роли датчиков определены;
- доступна статическая калибровка длительностью 3-5 секунд;
- синхронизация находится в допустимом диапазоне;
- частота и полнота потока достаточны;
- нет длительных пропусков, clipping или явного sensor drift.

Ввести состояния:

- `HIGH`;
- `MEDIUM`;
- `LOW`;
- `INVALID`.

При `LOW` и `INVALID`:

- не обновлять Correctness Score и Execution Effectiveness Score;
- не выдавать техническое "правильно/неправильно";
- показать конкретную проблему датчика;
- позволить безопасно завершить упражнение вручную.

**Готовность:** отключение IMU, рассинхронизация или плохой поток останавливают scoring, но не завершают аварийно всю сессию.

## 14. Этап 8: biomechanical pipeline

Реализовать поток:

```text
raw IMU
-> validation and timestamp normalization
-> synchronization and resampling
-> filtering
-> sensor fusion
-> calibrated relative thigh/shank orientation
-> knee angle and movement features
-> deterministic rep segmentation
-> ML movement interpretation with confidence
-> ROM, tempo, hold, consistency and error features
-> signal confidence
-> hybrid score and deterministic cue
```

Сначала включить только объяснимые метрики:

- knee flexion/extension angle;
- ROM per repetition;
- valid, incomplete and total repetition count;
- flexion/extension tempo;
- hold duration;
- active and paused duration;
- variation between repetitions;
- Signal Confidence.

Smoothness, jerk, frequency-domain features и ML quality classification допускаются только как исследовательские показатели до отдельной клинической и технической валидации.

**Готовность:** на размеченной replay-записи система воспроизводимо рассчитывает ROM и repetitions; расхождение с ручной разметкой фиксируется в validation report.

## 15. Этап 9: ML-модель интерпретации движения

ML-модель нужна не для свободного медицинского рассуждения, а для распознавания структуры и качества движения в IMU-временных рядах. Она работает локально на сервере и получает только данные после проверки качества, синхронизации и калибровки.

### Задачи модели

1. Определять тип упражнения из разрешённого набора, если сессия была начата пациентом.
2. Определять фазу движения: исходное положение, сгибание, удержание, разгибание, пауза.
3. Находить границы повторений.
4. Классифицировать допустимые для конкретного упражнения ошибки, например недостаточный ROM, слишком быстрый темп, отсутствие удержания или неполный возврат в исходное положение.
5. Возвращать confidence для каждого предсказания.
6. Формировать ML-компонент Correctness Score только при достаточном Signal Confidence и confidence модели.

### Что модель не делает

- не диагностирует осложнения;
- не определяет мышечную силу, нагрузку на сустав, боль, патологию, компенсаторное движение корпуса или таза;
- не заменяет измерение ROM и deterministic safety rules;
- не действует при низком качестве сигнала;
- не создаёт текстовые рекомендации самостоятельно.

### Входные признаки

Использовать не только абсолютные Euler angles из скрипта, а калиброванные и синхронизированные признаки:

- accelerometer и gyroscope по каждой оси;
- относительная ориентация thigh-to-shank;
- оценка knee flexion/extension angle;
- угловая скорость и ускорение;
- окна временного ряда фиксированной длины;
- ROM, tempo, hold и consistency features;
- signal-quality features;
- тип упражнения, сторона и версия калибровки как контекст, но не как замена измерений.

### Архитектура модели

Сначала создать простой и проверяемый baseline: gradient boosting или random forest на инженерных признаках для каждой exercise-specific задачи. Параллельно подготовить второй вариант для последовательностей: 1D CNN, TCN или компактный Transformer на оконных IMU-данных.

Не выбирать сложную модель по принципу "новее значит лучше". Выбрать модель по метрикам на отложенной выборке, устойчивости к реальному packet loss и объяснимости результата. Inference сервис должен возвращать label, probability, model version и список использованных feature versions.

### Данные и разметка

1. Собирать исходные синхронизированные сессии с согласием пациента.
2. Эксперт размечает exercise, фазы, repeat boundaries, валидность повторения и тип конкретной ошибки.
3. Делить train/validation/test по пациентам, а не случайно по окнам, чтобы исключить утечку личности между выборками.
4. Хранить labeler, дату, версию разметки и disagreement экспертов.
5. Отдельно балансировать классы: правильное выполнение, неполный ROM, быстрый темп, отсутствие hold и технические ошибки датчика.

### Безопасное внедрение

1. Сначала deterministic scoring остаётся основным.
2. ML запускается в `shadow mode`: предсказания сохраняются, но не показываются пациенту и не влияют на score.
3. Сравнить ML, правила и экспертную разметку на отложенных данных и пилотных сессиях.
4. После клинического утверждения добавить ML как versioned компонент hybrid Correctness Score.
5. При низкой confidence модели или расхождении с обязательным deterministic rule показать только нейтральный статус либо fallback к правилам.

### Обязательные метрики валидации

- precision, recall, F1 и confusion matrix для фаз и типов ошибок;
- MAE для ROM;
- precision/recall/F1 для valid rep detection;
- latency inference;
- calibration модели и distribution shift между пациентами;
- результаты отдельно по упражнению, стороне операции, POD phase и качеству сигнала;
- число случаев, в которых ML безопасно отключился по confidence gate.

**Готовность:** ML-модель локально обрабатывает replay-данные, возвращает versioned prediction и confidence, проходит shadow validation и не влияет на safety rules без клинического утверждения.

## 16. Этап 10: deterministic scoring и live feedback

Разделять пять разных сущностей:

| Показатель | Смысл |
| --- | --- |
| Correctness Score | Техника выполнения по доступным IMU-метрикам |
| Execution Effectiveness Score | Выполнение назначенного объёма, target и техники; не лечебный эффект |
| Clinical Response | Боль, симптомы, переносимость |
| Adherence | Выполнение назначенной программы |
| Signal Confidence | Техническая достоверность измерений |

Для каждого упражнения хранить versioned rules и версию ML-модели, если она используется. Итоговый hybrid Correctness Score должен сохранять отдельно deterministic и ML-компоненты, их confidence и применённый fallback. Пример допустимых live-cues:

- «Хороший темп»;
- «Двигайтесь немного медленнее»;
- «Удерживайте позицию»;
- «Вернитесь в исходное положение»;
- «Проверьте сенсоры».

Ограничения:

- один cue за раз;
- debounce, hysteresis и cooldown;
- cue появляется только при достаточном Signal Confidence;
- LLM не создаёт live cue;
- не давать замечаний о том, что три IMU не способны измерить.

**Готовность:** score обновляется после valid rep, а WebSocket UI показывает не более одного стабильного cue.

## 17. Этап 11: веб-интерфейс пациента

Реализовать экраны:

1. Сегодняшний план: POD, упражнения, длительность, кнопка «Начать».
2. Setup IMU: схема размещения, статусы THIGH/SHANK/FOOT.
3. Calibration.
4. Exercise: reference video, sensor status, rep counter, основной показатель, score и один cue.
5. Pause/stop с причиной.
6. Exercise result: valid/total reps, ROM, Correctness Score, Execution Effectiveness Score, Signal Confidence.
7. Post-session check: pain before/after, difficulty, knee feels, symptoms.
8. Progress: ROM, adherence, pain и выполненные сессии.
9. Сообщения врача.

UI требования:

- крупные интерактивные зоны;
- высокий контраст;
- масштабируемый шрифт;
- RU/KZ/EN из каталога переводов;
- простые формулировки;
- технические raw-графики не показывать пациенту.

**Готовность:** пользователь проходит сессию из replay-данных от начала до post-session check без ручных запросов к API.

## 18. Этап 12: веб-кабинет врача

Реализовать:

- dashboard "кому требуется внимание";
- очередь `stable`, `review`, `urgent`;
- карточку пациента: POD, операция, сторона, ограничения, план;
- тренды ROM, боли, adherence, score и symptoms;
- детализацию упражнения и технического качества;
- editor назначений;
- timeline: session, alert, review, изменение плана;
- weekly summary;
- сообщения пациенту;
- de-identified export для research viewer.

**Готовность:** врач видит источник каждого alert и меняет план с сохранением новой версии и audit trail.

## 19. Этап 13: safety layer и alerts

Safety engine должен быть полностью rule-based, versioned и конфигурируемым организацией/клиникой.

Уровни:

- `GREEN`: обычное продолжение плана;
- `YELLOW`: review врача;
- `RED`: остановка занятия и утверждённое срочное действие.

Примеры источников alert:

- ухудшение боли;
- новый отёк, покраснение, отделяемое из раны;
- боль в икре;
- внезапная одышка или боль в груди;
- низкая adherence;
- плато ROM;
- повторяющееся низкое качество IMU-сигнала.

Требования:

- пороги не зашиваются навсегда в код;
- alert объясняет триггер;
- есть duplicate suppression, cooldown и escalation;
- фиксируются acknowledge, dismiss и действия врача;
- RED не ставит диагноз, а показывает утверждённую инструкцию организации.

**Готовность:** LLM не может повышать, понижать или отменять severity alert.

## 20. Этап 14: локальная LLM

Создать отдельный `ai-orchestrator`, который обращается только к локальной модели.

### Разрешённые функции

- пациентский итог в 1-3 предложениях;
- объяснение фактических score components;
- нейтральное мотивационное сообщение;
- session/weekly summary для врача;
- черновик сообщения врачу;
- перефразирование уже выбранного deterministic cue без смены смысла.

### Запрещённые функции

- диагноз;
- назначение/отмена упражнений;
- изменение weight-bearing, нагрузки, дозировки или лекарств;
- свободная генерация технических live-cues;
- самостоятельное изменение severity safety alert;
- выдумывание ROM, симптомов, трендов или рекомендаций.

Передавать LLM только structured input. Валидировать ответ строгой JSON-схемой:

```json
{
  "patient_feedback": "",
  "clinician_summary": "",
  "coaching_cue_id": null,
  "safety_action": null,
  "facts_used": []
}
```

При недоступности LLM сессия, scoring и safety работают без неё.

**Готовность:** тест с отключённой LLM подтверждает, что пациент завершает сессию и получает score и safety instructions.

## 21. Этап 15: безопасность, журналирование и наблюдаемость

Реализовать:

- HTTPS/TLS между всеми внешними компонентами;
- безопасное хранение секретов;
- структурированные логи без ненужных медицинских данных;
- correlation ID от IMU packet до итогового score;
- метрики latency, packet loss, reconnect, quality and alert counts;
- резервное копирование PostgreSQL и object storage;
- разграничение clinical и de-identified research data;
- audit log для всех медицински значимых действий;
- ограничения скорости и защиту API.

**Готовность:** по session ID можно проследить путь от gateway до score, alert и действия врача.

## 22. Этап 16: тестирование и валидация

Порядок работ:

1. Unit tests для нормализации, формул, правил и score.
2. Contract tests API, WebSocket и IMU adapter.
3. Replay tests на сохранённых реальных записях датчиков.
4. Integration tests gateway -> backend -> database -> WebSocket UI.
5. E2E: врач создаёт пациента, пациент выполняет сессию, врач видит результат и alert.
6. Fault tests: потеря IMU, packet loss, disconnect, рассинхронизация, потеря сервера, недоступность LLM.
7. RBAC and tenant isolation tests.
8. Accessibility tests для веб-интерфейса.
9. Clinical validation с ручной экспертной разметкой ROM, repetitions и ошибок для каждого упражнения.

Пилот запрещён до утверждения клинической командой:

- финального списка упражнений;
- допустимых сенсорных placement;
- live-feedback whitelist;
- safety rules и контактных инструкций;
- score thresholds;
- validation protocol.

## 23. Definition of Done MVP

MVP считается готовым, если:

1. Несколько организаций изолированы друг от друга на уровне backend.
2. Врач создаёт пациента, операцию, ограничения и назначение.
3. Пациент проходит веб-сессию с тремя IMU через gateway либо replay simulator.
4. До упражнения выполняются проверка трёх сенсоров, калибровка и синхронизация.
5. Для первых трёх упражнений считаются repetitions, ROM и доступные метрики.
6. Correctness Score и Execution Effectiveness Score раздельны, объяснимы и versioned.
7. При низком Signal Quality scoring блокируется без ложного feedback.
8. Post-session symptoms доступны врачу.
9. Врач видит longitudinal trends и причину alert.
10. Изменение назначения сохраняет версию и audit trail.
11. ML-модель интерпретации движения проходит shadow validation и сохраняет prediction, confidence и версию модели; включение её в score требует клинического утверждения.
12. Локальная LLM не является зависимостью для safety, scoring или завершения сессии.
13. Все данные и результаты имеют data lineage.

## 24. Непосредственный порядок работы ИИ-агента

1. Не писать функциональность, пока не изучен текущий IMU-скрипт и не создан replay mode.
2. Создать репозиторий, Docker Compose, CI и базовую документацию.
3. Реализовать мультитенантную модель, RBAC, audit и базовые API.
4. Реализовать protocol engine, затем кабинет врача.
5. Реализовать IMU gateway simulator и hardware adapter.
6. Реализовать deterministic pipeline только для Heel Slide.
7. Подготовить экспертную разметку и ML shadow pipeline для Heel Slide.
8. Подключить patient web realtime flow.
9. Добавить Short Arc Quad и Ankle Pumps.
10. Добавить safety engine и clinician workflow.
11. Подключить local LLM через строго ограниченный orchestrator.
12. Провести replay, fault, security, ML shadow и clinical validation.
13. Только затем расширять библиотеку упражнений и начинать пилот.

После каждого этапа ИИ-агент обязан:

- показать изменённые файлы;
- запустить относящиеся к этапу тесты;
- описать известные ограничения;
- не переходить к следующему этапу при проваленных обязательных проверках;
- не добавлять медицинские правила, пороги или заявления без версии, конфигурации и клинического утверждения.
