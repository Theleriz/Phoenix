# Signal Quality и калибровка (этап 7)

`services/api/app/signal_quality.py` оценивает только техническую пригодность
потока. Это не биомеханическая интерпретация, не ROM, не rep segmentation и не
клиническая оценка.

Для каждой принятой gateway-записи API пересчитывает состояние текущей сессии,
сохраняет append-only результат в `signal_quality` и добавляет его к событию
WebSocket. Состояния: `HIGH`, `MEDIUM`, `LOW`, `INVALID`.

`INVALID` выдается при отсутствии одной из ролей, clipping или длительном
пропуске. `LOW` выдается, если ещё нет статического окна калибровки минимум в
3 секунды, поток ниже технической частоты 15 Hz или в окне есть заметное
вращение. `MEDIUM` сообщает, что базовый поток пригоден, но между последними
датчиками есть skew более 100 ms. `HIGH` означает, что все эти технические
проверки пройдены. Пороговые значения относятся только к development scaffold
и требуют device- и клинической валидации перед любым применением.

Поле `scoring_permitted` равно `false` для `LOW` и `INVALID`. В проекте пока
нет scoring engine, поэтому этот флаг блокирует будущую интеграцию по умолчанию
и не создаёт ни score, ни feedback. Synthetic replay намеренно остаётся
`LOW`, потому что его 0.2-секундный фрагмент не является калибровкой.

Пациент или уполномоченный специалист может запросить последний статус через
`GET /api/v1/rehab-sessions/{session_id}/signal-quality`. Endpoint применяет
tenant scope и обычную проверку доступа к пациенту. Он возвращает только
технический статус и конкретные причины; это не результат упражнения.
