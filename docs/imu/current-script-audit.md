# Аудит текущего IMU-скрипта

Дата аудита: 2026-09-05.  Источник: `sensor_script.py`, переданный владельцем
проекта. Текстовая копия помещена в `legacy/sensor_script.py`: содержимое
совпадает с источником после нормализации CRLF в LF, кроме одного добавленного
завершающего LF в копии. Это не изменяет исполняемое поведение; оригинал
`sensor_script.py` остаётся эталоном побайтного происхождения.
Лицензия и первоначальное происхождение не предоставлены; legacy-копию нельзя
распространять или лицензировать от имени PHOENIX до уточнения этих данных.

## Краткий вывод

Скрипт — диагностический Python-прототип для BLE, а не безопасный gateway. Он
может быть источником сведений для адаптера, но его клиническая
`interpret_movement()` не должна использоваться в PHOENIX. Её абсолютные
пороги `roll`/`pitch` не учитывают размещение датчика, калибровку, сторону
операции и относительную ориентацию thigh-to-shank.

В переданном файле есть блокирующая ошибка точки входа: строка
`if name == "main":` обращается к несуществующей переменной `name`. Нужная
форма была бы `if __name__ == "__main__":`, однако legacy-файл намеренно не
исправляется.

## Среда и BLE

| Область | Наблюдение |
| --- | --- |
| Язык | Python; `asyncio`, `struct`, `os`, `sys` (последний не используется) |
| Внешняя зависимость | `bleak`, классы `BleakScanner` и `BleakClient` |
| Discovery | Пятисекундное сканирование; имена с `WT`, `BWT`, `HC-08`, `JDY`, либо один захардкоженный MAC |
| Адреса | Один MAC `C9:CE:CE:5D:A9:BF`; прочие адреса назначаются в порядке discovery |
| GATT | Выбирается первый characteristic со свойством `notify`/`indicate`; fallback `0000ffe4-0000-1000-8000-00805f9b34fb` |
| Роли | Устаревшие `Left_Arm`, `Left_Leg`, `Right_Arm`, `Right_Leg`; для MVP нужны явно подтверждённые `THIGH`, `SHANK`, `FOOT` и сторона операции |
| Переподключение | Бесконечный цикл, фиксированная пауза 3 с; причина не записывается |

Автоматическое сопоставление MAC-адресов с ролями небезопасно и в новом
gateway запрещено. После первичного discovery модель, service UUID и
characteristic UUID должны быть подтверждены специалистом и сохранены в
настройках адаптера.

## Наблюдаемый формат данных

Handler накапливает BLE notification в буфер и ищет 20 байт. Первый байт должен
быть `0x55`, второй — `0x61`. Байты `2..19` разбираются little-endian как девять
`int16` (`<hhhhhhhhh`):

| Индекс | Поле | Текущее использование |
| --- | --- | --- |
| 0–2 | `ax`, `ay`, `az` | извлекаются, затем отбрасываются |
| 3–5 | `wx`, `wy`, `wz` | извлекаются, затем отбрасываются |
| 6–8 | `roll`, `pitch`, `yaw` | переводятся в градусы: `raw / 32768 * 180` |

Скрипт не сохраняет timestamp, sequence number, sampling rate, диапазон и
scale accelerometer/gyroscope, сырые значения или данные о потере пакетов.
Длина 20 байт полностью занята заголовком и 18 байтами payload: в коде нет
checksum. Поэтому checksum нельзя честно выводить из этого прототипа и каждый
пакет пока считается **неверифицируемым**. Нужна официальная спецификация
датчика для `0x61`.

## Ошибки и риски

- `except Exception: pass` скрывает BLE, GATT и ошибки разбора.
- При отключении очищается недоставленный буфер; нет durable buffer,
  heartbeat, cancellation или controlled shutdown.
- Нет device timestamps и межсенсорной синхронизации.
- Пакет валиден только по заголовку и длине; resynchronization может принять
  ложный пакет.
- Терминальный UI запускается отдельной бесконечной задачей; API/WebSocket
  событий нет.
- В исходнике нет обработки частичных payload с проверкой checksum и нет
  метрик частоты/pocket loss.

## Контракт нового адаптера

Новый gateway будет принимать поток `RawIMUPacket`, не выполняя клинических
выводов. Минимальные поля: `session_id`, `sensor_id`, подтверждённая роль
`THIGH|SHANK|FOOT`, `gateway_timestamp`, монотонный `sequence_number`, bytes
исходного пакета, accel/gyro/angles, явные scale/range акселерометра и
гироскопа, заявленная частота, версия
адаптера, а также статус валидации framing/checksum. Неизвестный checksum не
может помечаться как valid.

Интерфейс будет соответствовать плану:

```python
class IMUAdapter:
    async def discover(self) -> list[SensorInfo]: ...
    async def connect(self, sensor_id: str) -> None: ...
    async def stream(self) -> AsyncIterator[RawIMUPacket]: ...
    async def disconnect(self, sensor_id: str) -> None: ...
```

## Подтверждённая конфигурация WT901BLE68 (от владельца проекта, 2026-09-05)

| Параметр | Значение |
| --- | --- |
| Модель | WitMotion WT901BLE68 |
| Angles frame | `55 61 RollL RollH PitchL PitchH YawL YawH VersionL VersionH Checksum` (11 байт) |
| Checksum | Младший байт суммы всех предшествующих байтов кадра |
| Scale углов | `int16 / 32768 * 180°` |
| Частота BLE | 10 или 20 Гц — зависит от настройки прошивки; gateway обязан записывать фактическую настройку сессии |
| Диапазон accel | ±16 g |
| Диапазон gyro | ±2000 °/s |
| Координаты | Правая декартова система; направления X/Y нанесены на корпусе датчика |
| Временная синхронизация | Host-side timestamping: при получении пакета хост задаёт timestamp и объединяет три потока во временной кадр |
| Service UUID | `0000ffe5-0000-1000-8000-00805f9a34fb` |
| Notify characteristic UUID | `0000ffe4-0000-1000-8000-00805f9a34fb` |
| Планируемый лимит | Три одновременных датчика; заявленный практический предел host-адаптера — 5–7, но его нужно проверить на целевой ОС и адаптере |

Строка `Angles frame ... (11 байт)` выше — это то, что было заявлено владельцем
проекта. Живой BLE-захват с реальных трёх датчиков (раздел ниже) её не
подтвердил: фактическая нотификация — 20-байтный legacy-shape фрейм без
checksum. До получения официальной спецификации прошивки эта строка таблицы
не должна использоваться как источник истины для framing.

### Исправление base UUID по результатам GATT-дампа реального железа (2026-09-05)

Изначально заявленный base UUID (`...00805f9b34fb`, стандартный Bluetooth SIG
16-bit-to-128-bit base) не совпал с реальным hardware: `inspect_gatt.py`,
подключённый напрямую к трём физическим датчикам (`thigh`, `shank`, `foot`),
показал на всех трёх один и тот же нестандартный base UUID
`...00805f9a34fb` (отличие в одном символе, `9a` вместо `9b`) — известная
особенность части клонов BLE-модулей на базе HM-10/CC254x. Сервис `ffe5` и
notify-характеристика `ffe4` совпали с ожиданием. `SERVICE_UUID` и
`CHARACTERISTIC_UUID` в `capture_wt901ble68.py` и `scan_wt901ble68.py`
обновлены на подтверждённое значение; таблица выше отражает исправленный
UUID.

### Важное расхождение с legacy-прототипом

Legacy-скрипт наблюдал 20-байтный фрейм `55 61` с девятью `int16` (accel,
gyro, angles) и без checksum. Подтверждённая выше стандартная angles-посылка
WT901BLE68 имеет 11 байт и содержит только углы, версию и checksum. Их нельзя
считать одним форматом или применять parser 20-байтного legacy-фрейма к
11-байтным уведомлениям. До получения реального BLE capture нужно определить,
отправляет ли целевая настройка отдельные типы 11-байтных пакетов либо
агрегированный vendor-specific поток. Новый adapter должен поддерживать
versioned framing и отвергать кадры с неверной checksum.

### Подтверждение framing живым трёхдатчиковым BLE-тестом (2026-09-05)

Диагностический захват (`listen_raw.py`, затем `listen_raw_multi.py`) на всех
трёх физических датчиках (`thigh`, `shank`, `foot`) через исправленный
`0000ffe5-0000-1000-8000-00805f9a34fb`/`0000ffe4-...` показал устойчивый
20-байтный `55 61`-фрейм на всех трёх одновременно, без единого случая
11-байтного кадра. Пример декодирования одного кадра как
accel/gyro/euler (`<9h`, little-endian) дал физически правдоподобные значения
(accel около 1g суммарно, малый gyro-шум в покое, правдоподобные углы) —
это тот же layout, что уже реализован в `framing.WitMotion61FrameBuffer` и
`parser.WitMotion61Parser` (см. `Контракт нового адаптера` выше), изначально
написанных как раз под этот наблюдаемый 20-байтный shape.

`capture_wt901ble68.py` переписан, чтобы использовать этот существующий
framing/parser вместо отдельного 11-байтного `wt901ble68.py` (тот модуль и
его тесты не удалены — они остаются как каркас под гипотетический
альтернативный packet type, если он когда-либо подтвердится, но не
используются для захвата с этих датчиков). Каждая запись теперь несёт
`origin: "hardware"` и `validation_status: "unverified_checksum"`,
проставляемые `WitMotion61Parser` автоматически — как и раньше, эти записи
запрещены для score, ROM, повторений и клинического feedback.

Три параллельные подписки на одном Bluetooth-адаптере этого dev-хоста
подтверждены: за 20 секунд одновременного стрима получено 247 (thigh), 222
(shank) и 200 (foot) нотификаций — то есть ≈10–12 Гц на датчик, без обрывов
соединения и без признаков конкуренции за адаптер.

## Оставшиеся данные до hardware-интеграции

1. Три–пять коротких обезличенных записей реальных BLE notification-пакетов с
   назначенными ролями и указанием частоты 10 или 20 Гц. Они нужны для
   подтверждения реального framing, checksum и replay-тестов.
2. Официальная документация именно для текущей версии прошивки WT901BLE68 и
   реальные scale factors accel/gyro для тех packet types, которые будут
   включены. Угловой пакет `0x61` сам accel/gyro не содержит.
3. Подтверждение на целевом gateway-host: Bluetooth-адаптер, ОС, стабильность
   трёх параллельных подписок и поведение reconnect.

## Временное решение без hardware-данных

Владелец проекта подтвердил, что указанные данные пока недоступны, и разрешил
технический каркас с синтетическим replay. Он находится в
`services/imu-gateway`; его ограничения описаны в `synthetic-replay.md`.
Синтетические данные нужны только для контрактных, transport и UI-тестов и не
закрывают требования этого раздела к реальным записям и hardware validation.
