# Клиентское BLE-подключение датчиков

## Решение

Backend не подключается к датчикам напрямую и не должен: `imu-gateway`
уже трактуется как отдельный сетевой клиент API, аутентифицированный
`PHOENIX_GATEWAY_TOKEN` через HTTPS/WebSocket (см.
[`gateway-transport.md`](../imu/gateway-transport.md)). Поэтому физическое
место BLE-подключения не имеет значения для backend — важен только сетевой
доступ клиента до сервера и соответствие нормализованному контракту пакета
(`RawIMUPacket` в `services/imu-gateway/src/phoenix_imu_gateway/models.py`).

BLE-подключение выполняется на стороне пациента:

- в браузере через Web Bluetooth API (Chrome/Edge/Android) — без установки
  приложения, естественный путь для `patient-web`;
- нативным companion-приложением (например iOS/Swift), если понадобится
  поддержка платформ без Web Bluetooth (Safari/iOS его не поддерживает).

Гибрид — оба клиента одновременно, каждый шлёт один и тот же нормализованный
пакет на сервер — architecturally допустим и не считается костылём.

## Риск гибрида и как его снижать

Главный риск — расхождение BLE-логики (framing, resync, checksum,
sequence-numbering) между двумя независимыми реализациями (JS/TS и Swift).
Формат реального пакета уже расходился с изначально заявленной спецификацией
на этапе первого живого теста (см.
[`docs/imu/current-script-audit.md`](../imu/current-script-audit.md),
раздел «Подтверждение framing живым трёхдатчиковым BLE-тестом»); повторное
расхождение между платформами тем более вероятно, если не зафиксировать
единый источник истины.

Правило: контракт пакета и тестовые векторы (сырые BLE-байты →
ожидаемый нормализованный JSON) должны существовать один раз, версионированно,
и каждая платформенная реализация (браузер, iOS, будущий Android) обязана
проходить одни и те же векторы перед релизом. Версия адаптера
(`adapter_version` в `RawIMUPacket`) обязана отличаться по платформе, чтобы
инцидент можно было проследить до конкретного клиента.

## Реализация в браузере (2026-09-06)

`packages/ui/src/ble/` — TS-реализация Web Bluetooth-клиента для `patient-web`:

- `wt901ble68.ts` — framing/parsing, зеркалящий Python `WitMotion61FrameBuffer`/
  `WitMotion61Parser` байт-в-байт (тот же 20-байтный `0x55 0x61` кадр,
  без checksum). Тесты используют те же тестовые векторы, что и
  `test_parser.py`/`test_wt901ble68.py`, плюс декодирование реального
  захваченного кадра из живого теста — это и есть первый шаг к общим
  тестовым векторам из раздела выше.
- `connectSensor.ts` — `navigator.bluetooth.requestDevice()` по сервису
  `0000ffe5-...-9a34fb`, подписка на характеристику `0000ffe4-...-9a34fb`,
  парсинг уведомлений через `WitMotion61FrameBuffer`.
- Пакеты уходят напрямую в `POST /api/v1/gateway/imu-packets` с
  `origin: "hardware"`, `validation_status: "unverified_checksum"`,
  `adapter_version: "phoenix-patient-web-ble-0.1.0"` — версия адаптера уже
  отличается от Python-gateway (`0.1.0` без префикса), что и требовалось выше
  для трассировки инцидентов по платформе.

Требует secure context (HTTPS или `http://localhost`) и Chromium-браузер;
Safari/iOS по-прежнему не поддерживают Web Bluetooth вовсе.

Не реализовано в этом заходе, оставлено как есть намеренно:
`PHOENIX_GATEWAY_TOKEN` — общий секрет на всех пациентов, встроенный в
браузерный бандл через `VITE_PHOENIX_GATEWAY_TOKEN`. Достаточно для
демонстрации на своём контуре; для продакшена нужен скоупинг токена по
сессии/устройству до выдачи реальным пациентам (см. `main.py`
`gateway_token_is_valid()` — сейчас сравнение с одним значением из окружения).

## Открыто

- Общие тестовые векторы (raw bytes + JSON) пока продублированы (Python +
  TS с одинаковыми числами), а не вынесены в отдельный versioned package —
  формализовать при добавлении первого не-Python клиента, использующего
  другой language runtime, где текстовое дублирование перестанет быть
  тривиальным.
- Нативный companion-клиент не спроектирован; появляется только если
  потребуется поддержка iOS/Safari.
- Sequence-tracking на стороне браузера — простой монотонный счётчик на
  роль, без re-order/retry-буфера, который есть у Python-gateway
  (`DurableBuffer`/`SequenceTracker` в `services/imu-gateway`). Приемлемо для
  демо на локальной сети; для менее надёжного соединения нужно перенести и
  эту логику.
